## TL;DR

The current autonomous watch is **session-only** — it lives inside a Claude REPL
(`CronCreate`, `durable:true` didn't persist) and dies the moment that terminal
closes. To get a *true* 24/7 watch you need three things on an **always-on host**:

1. **A runner** — preferably the deterministic `scripts/ops/nexus-watch.sh`
   (already exists, costs $0/run, no LLM), with `claude -p` layered on top only
   for the cases that need reasoning.
2. **A scheduler** that survives reboots — `systemd --user` timer (preferred) or
   plain cron.
3. **Two credentials present in that host's environment** — Railway auth (for the
   443 token) + a Discord webhook (for paging). Optionally a Claude credential if
   you want the LLM-reasoning layer.

The cheapest, most robust 24/7 path is **bash-only** (`nexus-watch.sh` on a
systemd timer). It already does pull → threshold-eval → Discord-page-on-ALARM and
needs zero LLM tokens. Add `claude -p` as a *second, less-frequent* tier (e.g.
once/day or on-ALARM) for narrative reasoning the threshold table can't do.

| Piece | File | What it gives you |
|---|---|---|
| **443 data pull** | `pull-nexus-data.sh` | GET ~16 endpoints over HTTPS, token from Railway CLI (or `.env.local`), writes `data/pull/*.json`. Headless-safe (token read in subprocess, never echoed). |
| **Deterministic watch** | `scripts/ops/nexus-watch.sh` | READ-ONLY pull → 9-signal HEALTHY/WARN/ALARM eval → digest to Brain inbox → **Discord page on fresh ALARM** with a 180-min dedup window. `NEXUS_WATCH_PING=1` arms paging. **This is the 24/7 workhorse.** |

**Key point:** you do **not** need to write new watch logic. The 24/7 problem is
purely a *hosting + scheduling + credentials* problem. The logic is done.

## 2. Why the current path is session-only (the gap to close)

Per memory `project_autonomous_watch.md`: the watch is a `CronCreate` job inside a
live Claude session. `durable:true` did not persist, so:

- It fires only while that Claude REPL is open **and idle**.
- Closing Claude (or rebooting the laptop) kills it.
- It auto-expires after 7 days regardless.

So "re-arm each session" is a stop-gap. True 24/7 = move the trigger **out of the
Claude REPL** and onto an OS-level scheduler on a host that's always powered.

## 3. Host options (pick one)

Ranked by recommendation for this operator (who has a planned always-on PC).

### Option A — the operator's planned always-on PC (RECOMMENDED, $0 marginal)
- **What:** the dedicated PC the operator already intends to build/leave on.
- **Pros:** zero marginal cost; full control; same WSL/Linux environment as now,
  so the existing scripts run unchanged; can hold Claude credentials safely.
- **Cons:** must stay powered + online; home internet/power outages stop the watch
  (acceptable — cloud-side `fab56f3` is the fast-path safety net regardless).
- **Setup:** systemd `--user` timer (see §5). On WSL specifically, enable
  `systemd=true` in `/etc/wsl.conf` and ensure the WSL distro is set to not shut
  down (run a keep-alive or `wsl --shutdown` avoidance; a Windows Task Scheduler
  "at logon" `wsl.exe -d <distro> -- true` keeps it warm). Simpler: run the timer
  on a native Linux box, not WSL.

### Option B — a small cloud VM (RECOMMENDED if no reliable home PC)
- **What:** cheapest always-on Linux VM — e.g. Hetzner CX22 (~€4/mo), or a
  Railway/Fly/Oracle-free-tier micro instance, or a $5-6/mo DigitalOcean/Linode/
  Vultr droplet.
- **Pros:** truly always-on, datacenter power+network, independent of home.
  Already an external vantage point (good for worker-liveness checks).
- **Cons:** ~$5/mo; must install node + railway CLI + clone repo; credentials live
  on a remote box (use a scoped Railway **project token**, not the operator's full
  account login — see §4).
- **Rough cost:** $0 (Oracle Always-Free arm instance) to ~$6/mo (DO/Hetzner).
  The deterministic bash watch uses negligible CPU/bandwidth.

### Option C — Railway cron service (in-platform)
- **What:** a Railway "cron"-type service in the existing project that runs the
  watch on a schedule.
- **Pros:** same platform as the worker; Railway env vars already hold the
  webhooks + API key (no token copying — read them in-process).
- **Cons:** it's *inside* Railway, so it's a worse **external** observer (if
  Railway has a regional incident, both the worker and this watch are down — it
  can't page about the platform being down). Best used as a *complement*, not the
  sole watch. Also: this is a new service = a deploy change → operator-gated.
- **When to pick:** you want a second, in-platform watch in addition to a
  host-side one. Not the primary recommendation for the "external observer" role.

### Not recommended
- **GitHub Actions scheduled workflow** — `schedule:` cron works, but min ~5-min
  cadence, runners are ephemeral (no persistent dedup-state file → would re-page),
  and you'd be putting the Railway token + Discord webhook in GH secrets. Possible
  but the dedup-state loss makes it noisy. Skip unless A/B/C are all unavailable.

**Recommendation:** Option A (planned PC) as primary; Option B (cheap cloud VM) if
the PC isn't ready or you want datacenter-grade uptime + a genuinely external
vantage point. Option C only as an in-platform second layer.

## 4. Credentials the host needs (and how to provide them headless)

Three credentials, **two required** (Railway + Discord). The Claude one is only
for the optional LLM-reasoning tier.

### 4a. Railway / 443 token (REQUIRED)
The watch reads the API token via `railway variables --service API --kv`. On an
always-on host, do NOT rely on interactive `railway login`. Use a token env var:

- **`RAILWAY_TOKEN`** — a **project token** (scoped to one project+environment;
  create in Railway dashboard → project → Settings → Tokens). Preferred: least
  privilege, revocable, doesn't expose the operator account.
- or **`RAILWAY_API_TOKEN`** — account-scoped token (broader; only if a project
  token can't reach the API service vars).

Put it in the host's environment (systemd `Environment=` / an `EnvironmentFile=`
with `chmod 600`, or the cloud-VM's secret store). Then `railway variables
--service API --kv` works non-interactively. **Operator-gated:** creating/placing
this token is an operator action (secrets modification).

Fallback the script already supports: an `API_KEY=` line in `.env.local` on the
host. Same constraint — operator places it; never commit it.

### 4b. Discord webhook (REQUIRED for paging)
The watch pages via `NEXUS_WATCH_DISCORD_WEBHOOK` (else falls back to
`DISCORD_ALERTS_WEBHOOK_URL` in `.env.local`). Provide one of:
- `NEXUS_WATCH_DISCORD_WEBHOOK=https://discord.com/api/webhooks/...` in the host
  environment, or
- a `DISCORD_ALERTS_WEBHOOK_URL=` line in the host's `.env.local`.
Operator creates the webhook in the target Discord channel (a #firm-mobile /
#nexus-alerts channel). **Operator-gated** (secrets).

### 4c. Claude credential (OPTIONAL — only for the LLM-reasoning tier)
`claude -p` needs auth. Two ways:
- **`ANTHROPIC_API_KEY`** in the host env (pay-per-token; clean for headless), or
- copy the existing `~/.claude/.credentials.json` (subscription auth) to the host
  `~/.claude/`. Works but tied to the operator's login session/refresh.
For a headless box, `ANTHROPIC_API_KEY` is the robust choice. Operator authorizes
paying for premium tools when justified (memory
`feedback_operator_pays_premium`), so a metered key for the daily reasoning pass
is in-policy — but it's an **operator decision** to provision the key.

**Security note (binding):** never print these values; never commit them; never
read `.git/config` / `~/.ssh`. On a cloud VM, prefer `RAILWAY_TOKEN` (scoped,
revocable) over copying the operator's full `~/.railway/config.json`.

## 5. Setup steps (Option A or B — same scripts)

Assumes a Linux host (native or WSL-with-systemd) with the repo cloned at
`/home/nithu/code/ai-assistent` (adjust path on a cloud VM).

**0. Prereqs:** `node` (v20+), `git`, and the Railway CLI
(`npm i -g @railway/cli`). Clone the repo. `npm ci` is **not** needed for the
bash-only tier — `nexus-watch.sh` only needs `bash` + `curl` + `jq`. (Confirm
`jq` is installed: `which jq`.)

**1. Provide credentials** (operator, §4): export `RAILWAY_TOKEN` and
`NEXUS_WATCH_DISCORD_WEBHOOK` (or place `.env.local`). Verify:
```bash
RAILWAY_TOKEN=… railway variables --service API --kv >/dev/null && echo "railway OK"
```

**2. Smoke-test the watch, no paging:**
```bash
cd /home/nithu/code/ai-assistent
bash scripts/ops/nexus-watch.sh           # dry-run → digest, NO Discord
```

**3. Smoke-test paging once** (force an ALARM, confirm Discord fires):
```bash
NEXUS_WATCH_PING=1 NEXUS_WATCH_EXPECTANCY_USD=0 bash scripts/ops/nexus-watch.sh
# run it a 2nd time → should dedup (no 2nd page within 180 min)
```

**4. Install the systemd --user timer** (survives reboot; preferred over cron):

`~/.config/systemd/user/nexus-watch.service`
```ini
[Unit]
Description=Nexus client-side autonomous watch (read-only, pages on ALARM)
After=network-online.target

[Service]
Type=oneshot
WorkingDirectory=/home/nithu/code/ai-assistent
# secrets: keep this file chmod 600; do NOT commit it
EnvironmentFile=/home/nithu/code/ai-assistent/.nexus-watch.env
Environment=NEXUS_WATCH_PING=1
ExecStart=/usr/bin/env bash scripts/ops/nexus-watch.sh
```

`~/.config/systemd/user/nexus-watch.timer`
```ini
[Unit]
Description=Run Nexus watch every 30m during market hours, hourly off-hours

[Timer]
# every 30 min, 06:00–20:00 weekdays (CET-ish market window); tune to taste
OnCalendar=Mon..Fri *-*-* 06..20:00/30:00
# lighter off-hours sweep
OnCalendar=*-*-* 00..05,21..23:00:00
Persistent=true

[Install]
WantedBy=timers.target
```
Then:
```bash
systemctl --user daemon-reload
systemctl --user enable --now nexus-watch.timer
loginctl enable-linger "$USER"     # so --user timers run without an active login
systemctl --user list-timers | grep nexus-watch
```
`enable-linger` is what makes a `--user` timer truly 24/7 (runs without the user
being logged in). **Operator-gated** (this is the "turn it on" step — per
operator-prinsipp 1, Claude does not enable the cron/timer; operator does).

**Plain-cron alternative** (if not using systemd) — already in the watch runbook:
```cron
*/30 * * * 1-5 cd /home/nithu/code/ai-assistent && NEXUS_WATCH_PING=1 bash scripts/ops/nexus-watch.sh >> /tmp/nexus-watch.log 2>&1
```
(cron lacks `Persistent=` catch-up, but is simpler. On WSL, cron needs the distro
running — systemd+linger is more reliable.)

## 6. The LLM-reasoning tier (`claude -p`) — optional second layer

The bash watch catches *threshold* breaches. For narrative reasoning the table
can't express ("are these three small losses a regime-change pattern?",
"summarize what changed since yesterday and whether any activation actually
bit"), run a **less-frequent** `claude -p` pass — e.g. once/day after market
close, or triggered on-ALARM.

### Driver script (sketch — host-side, read-only)
```bash
#!/usr/bin/env bash
set -u
cd /home/nithu/code/ai-assistent
bash pull-nexus-data.sh                      # refresh 443 data first
claude -p "$(cat scripts/ops/watch-prompt.txt)" \
  --output-format text \
  --permission-mode plan                     # read/analyze only; no edits/writes
# pipe a concise verdict to Discord only if the model flags something:
```
- `--permission-mode plan` (or a tight allowed-tools list) keeps it read-only:
  it can read `data/pull/*.json` + repo docs and reason, but not edit/push/flip.
- Costs metered Anthropic tokens per run → keep cadence low (1×/day or on-ALARM),
  unlike the free bash tier (every 30 min).
- Have it **write** its analysis to `~/Obsidian/Brain/00-claude-inbox/nexus/`
  and only POST to Discord when it concludes the operator needs to act.

### The exact watch prompt to run (drop in `scripts/ops/watch-prompt.txt`)
> You are the Nexus 24/7 autonomous-watch reasoner. READ-ONLY: never edit code,
> never push/merge, never execute trades, never flip Railway env vars, never
> change strategy/risk/gate logic (Karri owns those — surface as a proposal note
> instead). The fresh 443 data is in `data/pull/*.json` (already pulled).
>
> Do this:
> 1. Read `data/pull/health.json`, `risk_snapshot.json`, `performance.json`,
>    `strategy_states.json`, `decision_funnel.json`, `threads_closed.json`,
>    `status_report.json`, `firm-activity-feed`/`activity_feed.json`.
> 2. If `strategy_states` shows session.state=WEEKEND/market closed and nothing
>    new since the last digest → write a one-line "quiet, market closed" note and
>    STOP (no Discord).
> 3. If open: verify recent activations actually BIT — adx/atr non-null
>    (INDICATOR_OANDA_FALLBACK), risk_events RISK_LEVEL blocks present,
>    calibration_log applied multipliers within SAFE_AUTO_APPLY ±20%/min-30,
>    shadow_forward_test rows growing.
> 4. Scan new closed trades for: hard losses, breaker/80u clamps, per-strategy
>    P&L skew, gate rejecting ~100%, expectancy/PF collapse, anomalies.
> 5. Write a dated digest to
>    `~/Obsidian/Brain/00-claude-inbox/nexus/<YYYY-MM-DD>/llm-watch-<TS>.md`
>    with a HEALTHY / WARN / ALARM verdict line + 3-6 bullet reasoning.
> 6. Output (for the wrapper to forward to Discord) a SINGLE final line:
>    `PAGE: <one-sentence reason>` ONLY if the operator needs to act now;
>    otherwise output `SILENT`. Do not page on known cold-start drag (lifetime
>    PnL includes pre-epoch backfill; thresholds are deliberately loose).
>
> Anything that looks like a strategy/risk fix → write it as a proposal bullet in
> the digest addressed to Karri; do NOT implement.

The wrapper greps the final line: if it starts with `PAGE:`, `curl` the rest to
the Discord webhook; if `SILENT`, do nothing. This keeps paging conservative and
the dedup logic simple. (Could also reuse `nexus-watch.sh`'s dedup-state file.)

## 7. How it reaches the 443 data + Discord (data/notify path)

```
[always-on host]
   │  systemd timer / cron  (every 30m, market hours)
   ▼
nexus-watch.sh
   │  railway CLI token (RAILWAY_TOKEN)  ── HTTPS/443 ──▶  api-production-b660.up.railway.app
   │                                                       (/health /firm/risk-snapshot
   │                                                        /analytics/performance …)
   ▼  writes data/pull/*.json  +  digest to Brain inbox
threshold eval → HEALTHY / WARN / ALARM
   │  on fresh ALARM (dedup 180m)
   ▼  HTTPS POST ──▶  Discord webhook (NEXUS_WATCH_DISCORD_WEBHOOK)  ──▶  operator's phone

[optional, 1×/day or on-ALARM]
claude -p (--permission-mode plan)  reads data/pull/*.json + docs
   │  writes llm-watch digest to Brain inbox
   ▼  final line PAGE:/SILENT → wrapper curls PAGE reason to same Discord webhook
```

- **Only outbound 443** is used both ways (data pull = GET, Discord page = POST).
  No inbound ports, no DB ports, no SSH — matches the firewall constraint.
- **De-dup vs cloud-side `fab56f3`:** keep host-side dedup window ≥ worker debounce;
  host-side does NOT alert on single-trade hard losses (server owns that). See the
  "Complement vs duplicate" section of `docs/ops/nexus-watch-runbook.md`.
- **Inbound mobile control** (optional, separate): run
  `scripts/firm/discord-listener.mjs` on the same host with `DISCORD_BOT_TOKEN` +
  `DISCORD_FIRM_CHANNEL_ID` so the operator can `!firm <cmd>` from the phone to
  poke the firm. Independent of the outbound watch.
